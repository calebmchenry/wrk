# Sprint 001: Combined Critique of GPT56SOL and GPT55

This review covers only [GPT56SOL](SPRINT-001-GPT56SOL-DRAFT.md) and [GPT55](SPRINT-001-GPT55-DRAFT.md), grounded in the [intent](SPRINT-001-INTENT.md), [milestone ticket](../../../.wrk/wrk-682f60c7.md), [parent ticket](../../../.wrk/wrk-3f8a21b7.md), [ticket format](../../ticket-format.md), [configuration](../../configuration.md), and repository agent rules.

Go, macOS/Linux, serialized CLI writers with stale-file checks and the documented final editor race, creation-time `--parent`, `--priority`, repeatable `--label`, `--no-labels`, and strict failure for ordinary commands on invalid projects are resolved. Their appearance as exclusions or open questions is obsolete, not a reason to reopen the interview.

**Recommendation:** use GPT56SOL as the structural base and GPT55 as a guide to keeping implementation small. Neither is ready unchanged: storage guarantees, custom-value compatibility, recovery guidance, and completion gates need correction.

## GPT56SOL assessment

**Strengths.** This draft translates requirements into implementable boundaries: typed requests/results, byte-oriented body splitting, retained YAML nodes, complete snapshots, separate relationship graphs, deterministic diagnostics, and named storage hooks. Its staging-plus-hard-link creation protocol distinguishes complete publication from merely avoiding overwrites. It correctly explains the final comparison-to-rename race, aggregates validation diagnostics, specifies command-local flag parsing, and maps work to concrete files. Copied fixtures, subprocess tests, clean-source execution, and live CLI dogfooding form a credible verification sequence.

**Weaknesses and risk gaps.** The most serious defects are within otherwise precise contracts:

- **The lock inode is unstable.** Locking `.wrk/config.yaml` cannot guarantee CLI serialization when permitted config editing replaces that file. Writer A can hold the old inode while writer B locks the replacement; both then hold apparently exclusive locks. Use a dedicated persistent lock file, never unlink it on release, and exclude it from tickets and Git. Test config replacement while a writer holds the lock. This is separate from the accepted final ticket-editor race.
- **Snapshot promises exceed the checks.** After acquiring the lock, the draft compares the full snapshot, but immediately before publication it checks only the update target. Config, another ticket, or the inventory can change during staging; `new` has no corresponding final target comparison. Recheck relevant snapshot inputs immediately before publication and describe the remaining non-atomic observation window accurately. Do not promise detection of every change before commit.
- **JSON convenience narrows storage compatibility.** The proposed rejection of timestamps, binary values, non-string nested keys, aliases, tags, and non-finite numbers is not established by the normative custom-field rules. Those rules permit unconfigured values and require preservation. Identifying this as a question is helpful; making the restriction a phase-two dependency prematurely decides it. Storage validity and JSON representation need distinct contracts.
- **Recovery contradicts repository policy.** “Users repair malformed files directly” and the risk-table recommendation of direct repair conflict with CLI-only ticket metadata mutation. Body and config edits are permitted; manual frontmatter repair is not. Strict validation deliberately prevents ordinary `update` from repairing invalid projects. Acknowledge that limitation rather than creating an undocumented bootstrap exception.
- **Discovery has an unsafe ambiguity.** Stopping only at a real, non-symlink `.wrk` directory could skip an unacceptable inner entry and discover an outer project. Refuse an encountered symlink or unusable `.wrk` boundary explicitly. Likewise, clarify that ID-shaped symlinks/nonregular entries are diagnosed rather than silently excluded before validation.

**Missing edge cases.** Add config replacement under lock, unrelated-file changes during staging, read errors and short writes, config creation interrupted midway, and errors after successful link/rename. The three real tickets contain neither an old prefix distinct from current config nor nested custom values; synthetic fixtures must cover those claims. Specify temporary-file permissions explicitly: a temp-file API's restrictive default mode does not automatically implement the intended final creation mode.

**Definition of Done.** Broad coverage is strong, but requiring all failed I/O paths to leave preexisting files byte-identical is impossible after publication. Directory sync, temporary-name removal, or output delivery can fail after the ticket has changed. Also remove the option to reduce support to macOS: Linux is confirmed scope, so missing Linux evidence leaves the milestone incomplete. Add the three newly confirmed creation override flags throughout commands, tests, documentation, and dogfooding scope.

## GPT55 assessment

**Strengths.** The smaller package layout and seven phases are easy to follow. The draft preserves the milestone/parent distinction, combined updates, independent graphs, exact body bytes, configured defaults, isolated fixtures, and CLI-only dogfooding. It correctly warns that rename alone does not prevent lost updates and proposes deterministic conflict hooks. Its restraint around databases, editor integration, and general metadata updates is appropriate.

**Weaknesses and risk gaps.** Much of its apparent simplicity comes from leaving difficult decisions to implementation:

- **Exclusive creation is insufficient.** Opening the final ticket path with exclusive-create semantics prevents clobbering but exposes an empty or partial ticket during writing and can leave one after interruption. A strict reader may then reject the entire project. Stage and close complete bytes before atomic no-replace publication; apply the same principle to `config.yaml` during `init`.
- **Writer coordination is incomplete.** Only updates clearly acquire a lock. `new` must use the shared writer protocol too. Acquiring a lock after validation and rereading only the target leaves changes to config, relationship targets, and ticket inventory undetected. Specify a stable lock inode, snapshot revalidation, release behavior, and a final comparison after staging, not just before the temp-file write.
- **YAML preservation is an intention, not an algorithm.** Node parsing is necessary but does not define recursive duplicate detection, scalar-tag preservation, exact numeric handling, aliases, or JSON conversion. Unmarshalling nodes into generic values can still change unrelated custom data. Define the retained storage representation and the title/status patch operation before commands consume it.
- **Contracts remain negotiable.** “Unless implementation finds a simpler” list ordering is unsuitable for a stable automation interface. Global versus command-local `--json`, error streams/envelopes, general I/O exit codes, initialization behavior, and diagnostic aggregation remain incomplete. The invalid-project policy must now be unambiguous: ordinary commands fail without partial successful results.

**Missing edge cases.** Beyond storage failures, specify LF/CRLF delimiter boundaries, closing delimiters at EOF, invalid UTF-8, absent versus explicit-null optionals, old-prefix discovery, recursive duplicate keys, and parent-depends-on-child validity. Existing body tests are useful but do not establish these parser rules. Config changes must not retroactively apply creation defaults to stored tickets.

**Definition of Done.** The checklist covers the happy path and major schema failures, but lacks enforceable gates for two-process serialization, atomic creation visibility, complete-snapshot conflicts, post-publication outcomes, parseable JSON errors, new override precedence, and actual Linux execution. It should name required evidence rather than rely on “failure atomicity” as an umbrella. The file list also needs `go.sum`, a command-contract document, concrete storage test files, and explicit agent-documentation updates.

## Cross-draft contradictions and merge recommendations

The architectural differences are compatible; the behavioral differences require one decision each:

| Topic | GPT56SOL | GPT55 | Merge recommendation |
| --- | --- | --- | --- |
| Ordering | Lexicographic ID | Status, priority, ID; negotiable | Use ID ordering consistently for this milestone. |
| JSON placement | Command-local | Global in implementation phase | Adopt documented command-local placement, including flags after positionals. |
| Exit codes | `1` I/O/conflict, `2` usage, `3` invalid data | `1` validation/input, `2` config/discovery, `3` conflict | Adopt 5.6's mapping; define discovery failures and retain machine-readable error codes. |
| Existing support-only `.wrk` | Allow initialization | Wording suggests blanket refusal | Allow staged config publication without replacing support files. |
| Creation overrides | Explicitly deferred | Deferred absent authorization | Implement all confirmed creation flags; defer corresponding updates. |

**1. Make the storage protocol the first feasibility gate.** Adopt the 5.6 staging approach with a permanent `.wrk/.lock`; ordinary read commands and `validate` must not create it. Explain initialization when `.wrk` or config is absent, lock wait/error behavior, abandoned temp names, permission handling, and unsupported filesystem operations. Use exclusive temp creation and same-directory publication; do not fall back to streaming directly into the final name. Read stdin before taking a long-lived writer lock. Run deterministic two-process tests as well as injected hooks: hooks alone cannot prove lock coordination.

**2. Define publication as an explicit boundary.** Before link/rename succeeds, failures leave existing tickets unchanged and no new final ticket visible. After it succeeds, rollback is not generally safe: another process may already have observed the result. Track whether publication occurred, report affected ID/path plus committed state where reporting remains possible, distinguish durability uncertainty from cleanup failure, and explain recovery when stdout delivery fails. Retrying a committed `new` blindly can create duplicates. Inject failures before publication, after publication, during directory sync, during temp cleanup, and during output. For initialization, document whether an empty `.wrk` scaffold can remain after failure without ever exposing partial config bytes.

**3. Separate YAML storage from JSON projection.** Preserve untouched YAML nodes and body bytes; do not round-trip stored custom values through JSON or `float64`. Choose a documented representation for YAML values that JSON cannot directly express, such as tagged value objects, rather than declaring the project invalid solely for output convenience. Any narrower accepted YAML subset requires an explicit format decision and compatibility rationale. Test nested unconfigured maps/sequences, nulls, quoted scalar lookalikes, large integers, and representative non-JSON YAML values. Resolve alias/tag behavior and projection failures before marking semantic preservation complete; avoid promising exact frontmatter formatting.

**4. Integrate resolved interface decisions everywhere.** `--priority` overrides configured priority; repeated `--label` values replace configured labels; `--no-labels` explicitly selects an empty list. Reject combining labels with `--no-labels`, empty labels, and repeated scalar flags; define duplicate-label handling. Keep creation parent validation and all four status semantics. Remove obsolete interview questions and follow-ups for creation overrides. Follow-up tickets still belong under the open parent for relationship, priority/label, and custom-field *updates*. Preserve the prohibition on hand-created or manually repaired ticket metadata; document the recovery limitation and track a sanctioned repair design separately.

**5. Keep file ownership concrete without multiplying abstractions.** The repository has no implementation to extend. Use the 5.6 file map, consolidating packages where appropriate, with acyclic dependencies: codecs/domain below snapshot and graph validation, application orchestration above storage. Specify the YAML dependency version and verify its node round-trip behavior before relying on it. Make the stated build constraint explicit in `lock_unix.go`: `_unix.go` alone is not a GOOS filename constraint; use `//go:build darwin || linux`. Add named storage failure/concurrency tests, JSON projection tests, and `.gitignore` entries for lock/temp artifacts. Keep output schemas out of normative storage rules unless a deliberate format clarification is required.

**6. Close the remaining assumptions through evidence.** The Go minimum/module identity, YAML edge semantics, precise init behavior, JSON failure contract, and Linux test environment still need concrete choices. A clean copied source tree is a reasonable local build gate while no commits exist; record it honestly and verify installation as documented. Neither a canonical public module path nor public packaging should block local dogfooding. Full-snapshot validation has an acceptable initial cost, but keep it measurable; do not add caches that weaken correctness. Completion requires the full subprocess workflow on macOS/Linux, unchanged fixture inputs, documented publication outcomes, and CLI-created follow-ups before marking only the milestone done.
