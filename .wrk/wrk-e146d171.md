## Outcome

Allow existing tickets to change priority and labels through `wrk update`, extending the current creation-time overrides.

## Scope

Define explicit replacement/add/remove/clear semantics for labels and their conflicting flags. Priority uses the existing low/normal/high/urgent vocabulary. Preserve the current schema rule that duplicate labels are not forbidden. Configured defaults continue to affect only new tickets.

## Acceptance criteria

- [x] Support priority changes through the CLI.
- [x] Support documented label update and explicit empty-label operations.
- [x] Combine supported metadata flags into one validated update with clear conflicts and no-op results.
- [x] Preserve exact bodies, unrelated custom values, omitted fields, permissions, and safe publication guarantees.
- [x] Verify human/JSON output, invalid input rejection, and default changes that never alter existing tickets.
- [x] Add meaningful tests on supported platforms and update indexed docs.

## Completion decisions (before implementation)

- Add `update --priority low|normal|high|urgent`, repeatable `--label value` for whole-list replacement, and `--no-labels` for an empty list, matching the creation vocabulary. Priority is scalar and repeated priority/clear flags remain usage errors.
- Replacement preserves the requested source order and duplicates; JSON summaries remain sorted. Exact list equality is a no-op. Clearing absent/already-empty labels is a no-op and does not insert an omitted field. An omitted priority has the fixed effective value normal: setting normal is a no-op, independent of current creation defaults. Setting another priority inserts only that field.
- `--label` conflicts with `--no-labels`; either replacement/clear conflicts with any `--add-label` or `--remove-label`, regardless of flag order. Existing add/remove overlap rules stay unchanged. Label values remain nonempty UTF-8 strings. Invalid priorities fail complete-candidate validation without publication.
- Single-ticket title/status/priority changes can combine with any one label mode in one validated mutation. Recursive updates accept all label-only modes, reusing the existing snapshot, locking, per-file publication and retry behavior, and reject title/status/priority. Replacement/clear intentionally replace/remove every target's entire label list; use add/remove to retain unrelated labels.
- Extend the shared `ticket.Changes`/`PatchChanges` path rather than creating another mutation engine. Detach aliases of changed priorities and label lists/elements, retain exact bodies and unrelated values/omissions/modes, and reuse staging, stale-input checks, and committed-error reporting.
