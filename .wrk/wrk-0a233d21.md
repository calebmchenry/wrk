## Outcome

Users can run an arbitrary command sequentially over a wrk query, re-evaluating current ticket data after each successful action. The same command can optionally keep waiting for new work. Codex burns become a documented use of this runner instead of a separate orchestration loop.

## Accepted behavior

- `wrk run <filters> -- <command> <arguments...>` reuses wrk list selection and explicit project/config resolution. Select the first matching ticket not successfully processed earlier in this invocation.
- Replace literal `{id}` in child arguments while preserving argument boundaries. No implicit shell, shell expansion, aliases, pipelines, or redirection. Users can explicitly invoke an interpreter or their own script.
- Run one child at a time in the resolved project root, inheriting exported environment variables and PATH. Keep child input noninteractive. Project selection stays fixed for the invocation.
- Default success means exit 0. `--expect-status done` additionally requires the same ticket's persisted status to be done. Nonzero exits and failed completion checks stop immediately, including in streaming mode.
- Only record an ID as processed after every configured success check passes. Skip successful IDs for the rest of this invocation, including across polls and later status changes. A new invocation has a fresh set. This deliberately replaces the burn script's repeated-selection failure: review and labeling actions can succeed without removing a ticket from the query.
- Ordinary mode re-queries immediately after success and exits when no unprocessed matches remain. `--stream` instead waits between idle queries and continues until interruption, failure, or a success-count limit.
- Support selecting a specific ticket for an explicit retry even if it is no longer ready. Retry starts the supplied command from the beginning. The script owns recovery from partial side effects and must be safe to rerun when used that way.
- The runner does not change ticket metadata automatically. For multi-step implementation scripts, keep the ticket unfinished until the whole required workflow succeeds.
- Explain selection filters, order, match counts, action, success requirements, waiting state, failures, and final outcome. Preserve child logs and provide newline-delimited JSON lifecycle events.

## Initial implementation defaults

These fill details not prescribed by the user; implementers can resolve routine syntax details without reopening the accepted behavior:

- Preserve existing list defaults/filter semantics and ID-ascending ordering; no new sorting subsystem. Burn examples explicitly use `--ready` and `--expect-status done`.
- Use `--ticket <id>` for one-off execution, separate from query selection and streaming.
- Use `--max-tickets N` for a positive successful-action limit; distinguish action success from a ticket's done status.
- Use `--poll-interval 5s` as the idle-stream default and retain a configurable approximately 60-second heartbeat.
- Store timestamped run logs and numbered action logs under the selected project's ignored `.wrk-runs/`, with an explicit log-directory override whose relative path is resolved from the invocation directory. Logs are diagnostic artifacts, not resumable workflow state.
- Retain exit categories 0 for a drained query/success limit/successful explicit ticket, 1 for execution or completion failure, 2 for usage errors, and 130 for interruption.
- Support the repository's existing macOS/Linux platform contract.

## Boundaries

The user explicitly chose a small first version informed by later usage feedback. Do not add named steps, checkpoint/resume databases, workflow definitions, automatic retries, rollback, Git automation, automatic status transitions, built-in AI providers, parallel workers/claims, a full-screen TUI, or `list --stream`. Arbitrary scripts may contain multiple agent/Git steps; wrk observes one action and its configured success checks.

Do not hold the ticket writer lock across child execution or idle waiting. Child CLI writes, direct body edits, and Git operations retain the existing external-editor boundary. Sequential execution within one runner does not coordinate independent workers.
