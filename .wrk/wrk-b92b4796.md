## Outcome

Assess the first real-project report that wrk run stalled after a ticket became in-progress but was not marked done. Recommend which responsibilities belong to the runner and the supplied action. This is investigation and advice, not authorization to implement changed run semantics.

## Acceptance criteria

- [x] Inspect current selection, completion checks, recovery commands, and accepted design decisions.
- [x] Distinguish a failed completion check from an idle or drained ready queue.
- [x] Recommend a practical recovery path and identify any proposed product improvement without treating it as an accepted decision.
- [x] Record verification and validate the project.

## Context

Existing completed work: wrk-8f6d1169 (design decisions), wrk-59020e2f (engine), wrk-7b831fa1 (output), wrk-ef04f589 (burn migration).

The user confirmed that the runner exited because the ticket was not done. The exact invocation and child logs were not supplied, so whether implementation was complete or genuinely unfinished remains unknown. The checkout already contained a modification to .wrk/wrk-ef04f589.md; it was preserved.

## Findings and recommendation (2026-10-14)

The reported stop matches the deliberate completion-check contract: after a child exits, internal/runner/runner.go reloads the project and rejects a persisted status that differs from --expect-status. It stops before starting another ticket. --ready selects only todo tickets with done dependencies, so restarting that queue does not resume the in-progress ticket. --ticket selects it explicitly without resetting its status. Current failure output already includes logs, observed/required status, and a copyable retry command.

Keep the core completion check and readiness semantics. Process exit cannot establish acceptance, and in-progress may represent genuinely unfinished work or another worker. Do not automatically mark done, reset to todo, or broadly reselect in-progress tickets.

The first improvement should be the supplied action's closeout protocol: inspect existing work, satisfy acceptance criteria, run required verification, record evidence, and explicitly mark done before returning when complete. If incomplete, record the reason and next step with an accurate status. The bundled burn wrapper currently supplies only `Implement {id}`, relying on repository instructions for this protocol; improving that default is a useful repository-side change, not solely a burden on users.

If missed closeout persists, consider one bounded reconciliation pass in the agent wrapper after an exit-0 action leaves a valid in-progress ticket. It should inspect actual work and verification, complete only what it can justify, and leave a real blocker unresolved for the runner to report. This is a proposal, not an accepted implementation decision. Generic opt-in retries could be reconsidered later with evidence; automatic retries and checkpoints were explicitly excluded from the original runner scope.

Immediate recovery: inspect the ticket, logs, and changes. If all criteria are verified, explicitly close it; otherwise use `wrk run --ticket <id> --expect-status done -- <original action>` to rerun the action after inspection, then restart the queue. The action restarts from the beginning and must account for partial effects.
