## Outcome

Link items for context without implying hierarchy or prerequisite order. Related links are navigable from either endpoint and have no effect on readiness/status.

## Acceptance criteria

- [x] Define and document a minimal related-item representation and its canonical storage/reciprocal-display rules; avoid inconsistent duplicated edges or undocumented multi-file atomicity assumptions.
- [x] Support creation and incremental add/remove through the CLI and shared store. Define repeatability, conflicts, no-ops, clearing, and combination with other single-item updates.
- [x] Validate same-project existing endpoints and reject self/duplicate links; allow cycles in this contextual relationship, independently of parent/dependency cycle checks.
- [x] Expose both outgoing/incoming context as one deduplicated related-item view in show/API/browser. Add/remove from the browser must have documented semantics from either endpoint.
- [x] Reuse shared conflict/locking/publication handling and preservation guarantees. If the chosen representation touches multiple files, explicitly define partial-publication and retry behavior.
- [x] Support browser navigation and live refresh for link changes made by agents; preserve unsaved drafts and respect expected revisions.
- [x] Preserve parent/dependency/status semantics and all unrelated metadata/custom fields/body content.
- [x] Decide format-version and older-client compatibility deliberately before landing the schema extension; document upgrade requirements and do not silently invalidate existing files.
- [x] Test CLI/store/HTTP/browser parity, references, reverse display, no-op behavior, cycles, removal, live refresh, and stale edits; update ticket-format/configuration/CLI docs as applicable.

## Scope

Exactly one general related-to relationship. External URLs remain ordinary Markdown links. Cross-project linking, configurable link types, and relationship-driven automation are deferred.

## Implementation decisions

- Optional version-1 `related` ID list stores each unordered pair once, on the endpoint that first adds it. Reciprocal display is derived; reverse duplicates are invalid. Existing version-1 files require no migration; older strict clients must be upgraded before using this field.
- Creation stores outgoing links in the new file. Updates add/remove from either endpoint; reverse adds are no-ops, removal finds the owner, and `--no-related` clears all incident links. Related cycles do not affect readiness or other graphs.
- Reverse removals may touch multiple owners alongside ordinary changes to the addressed item. Reuse staged batch publication under one lock, reporting each target's committed/unchanged/pending state; partial publication is explicit and requires inspection before retry.
- Exact-source revisions remain unchanged. A separate derived `related_revision` protects browser drafts against incoming/outgoing link-set changes, checked under the same lock. Live updates retain draft inputs and both original preconditions; explicit review reconciles add/remove intent.
- CLI creation uses repeated `--related`; update uses `--add-related`, `--remove-related`, or `--no-related`. HTTP and the browser editor use the shared store. The docs cover all flags, errors, result shapes, compatibility, and retry behavior.
