## Outcome

Link items for context without implying hierarchy or prerequisite order. Related links are navigable from either endpoint and have no effect on readiness/status.

## Acceptance criteria

- [ ] Define and document a minimal related-item representation and its canonical storage/reciprocal-display rules; avoid inconsistent duplicated edges or undocumented multi-file atomicity assumptions.
- [ ] Support creation and incremental add/remove through the CLI and shared store. Define repeatability, conflicts, no-ops, clearing, and combination with other single-item updates.
- [ ] Validate same-project existing endpoints and reject self/duplicate links; allow cycles in this contextual relationship, independently of parent/dependency cycle checks.
- [ ] Expose both outgoing/incoming context as one deduplicated related-item view in show/API/browser. Add/remove from the browser must have documented semantics from either endpoint.
- [ ] Reuse shared conflict/locking/publication handling and preservation guarantees. If the chosen representation touches multiple files, explicitly define partial-publication and retry behavior.
- [ ] Support browser navigation and live refresh for link changes made by agents; preserve unsaved drafts and respect expected revisions.
- [ ] Preserve parent/dependency/status semantics and all unrelated metadata/custom fields/body content.
- [ ] Decide format-version and older-client compatibility deliberately before landing the schema extension; document upgrade requirements and do not silently invalidate existing files.
- [ ] Test CLI/store/HTTP/browser parity, references, reverse display, no-op behavior, cycles, removal, live refresh, and stale edits; update ticket-format/configuration/CLI docs as applicable.

## Scope

Exactly one general related-to relationship. External URLs remain ordinary Markdown links. Cross-project linking, configurable link types, and relationship-driven automation are deferred.
