## Outcome

Allow browser edits to title/body/metadata without overwriting changes made by an agent since the browser loaded the item. Provide shared body-update support usable from the CLI and HTTP layer.

## Acceptance criteria

- [x] Extend shared ticket/store updates with an explicitly supplied UTF-8 body; omission preserves the existing exact body, and an empty supplied body clears it.
- [x] Add wrk update <id> --body-file path|- with input read before locking. Permit a body and supported single-item metadata changes in one validated mutation; retain label-only recursive behavior.
- [x] Expose an opaque item revision to readers and a store-level expected-revision precondition checked after acquiring the project lock and loading current data.
- [x] A changed or deleted target since the browser's original read produces a recognizable conflict/not-found result with no publication, including when the change predates the HTTP request. A stale no-op must not silently acknowledge an obsolete edit.
- [x] Revalidate current configuration and whole-project relationships for every write. Retain final snapshot comparisons for changes during mutation; do not require all unrelated item edits to invalidate an otherwise current item draft.
- [x] Document precisely which bytes/state a revision covers and which concurrency races remain under the accepted external-editor/Git boundary.
- [x] Preserve unrelated YAML semantics, custom values, permissions, omitted metadata, no-op behavior, and publication/committed-error reporting.
- [x] Test exact body bytes, empty/no-final-newline/CRLF bodies, combined updates, invalid input, stale browser revision after CLI/body edits, no-op conflicts, publication failures, and successful retries after explicit reload.
- [x] Update CLI/ticket/storage documentation and meaningful store/CLI integration coverage.

## Implementation context

Current store locks and final comparisons protect a mutation's own snapshot; they do not cover the time a browser form is open. Extend internal/ticket and internal/store rather than creating a second write path. Browser conflict presentation belongs to the editing ticket.

## Implementation decisions (2026-10-08)

- Use an optional body string in shared changes: omitted preserves and explicitly empty clears. CLI input is read before project discovery/locking, and body edits stay single-item only.
- Expose an opaque source-content revision in every JSON ticket summary. It covers exact frontmatter/body bytes, excluding config, other tickets, inode identity, modes, and timestamps. Identical restored bytes share a revision.
- Check an optional store expected revision under the writer lock before candidate/no-op handling. Missing targets return NOT_FOUND and changed/unreadable targets return CONFLICT, including invalid external rewrites. Current project validation and final full-snapshot comparisons remain mandatory before publication.
- Revision preconditions are single-item only. HTTP/UI integration remains in later tickets; no CLI revision flag is introduced here.
- Implementation and verification are complete. Browser callers will use the shared revision precondition in the later editing ticket.
