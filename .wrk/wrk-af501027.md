## Outcome

The release-to-upgrade path is exercised on supported systems and documented for users, agents, and maintainers.

## Acceptance criteria

- [ ] Add end-to-end tests that build/install two identifiable release binaries into disposable directories and perform check, upgrade, re-execution of the new version, and a subsequent no-op. Exercise the real download/checksum/archive/replacement path through controlled release fixtures.
- [ ] Demonstrate executable replacement on both macOS and Linux; smoke-test release assets for the supported architecture matrix and report actual runtime coverage separately from cross-build results. Do not substitute cross-compilation for runtime evidence.
- [ ] Exercise interrupted/truncated downloads and pre-publication failures with the old binary still runnable, concurrent invocations, and errors after publication with accurate diagnostics. Include JSON and operation outside or inside an invalid/unsupported-format project.
- [ ] Run repository development checks and `go run ./cmd/wrk validate`; wire repeatable upgrade tests into the release gates from [wrk-f28fed55](wrk-f28fed55.md).
- [ ] Update README and `docs/cli.md` with version/check/upgrade commands, stable-only/no-downgrade behavior, exit codes/JSON fields, supported installations, permission/symlink guidance, and troubleshooting for offline/rate-limit/integrity failures.
- [ ] Document that older binaries without the upgrade command need one manual install of an upgrade-capable release. Coordinate that first release with [wrk-551ff6c2](wrk-551ff6c2.md); do not publish artificial stable versions solely to manufacture test evidence.
- [ ] Document maintainer expectations for immutable published version/assets, matching checksums, latest-stable selection, platform coverage, and upgrade compatibility; link new maintainer guidance from `docs/index.md`.
