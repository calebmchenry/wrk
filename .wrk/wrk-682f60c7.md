## Command contract

| Command | Behavior |
| --- | --- |
| `wrk init` | Create `.wrk/` and its config in the requested directory, defaulting to the working directory, without overwriting existing files. |
| `wrk new "Title"` | Create a ticket using the configured prefix and defaults; print its ID and path. |
| `wrk new "Title" --body-file <path>` | Read the initial Markdown body from a file; `--body-file -` reads standard input. |
| `wrk list` | List active tickets (`todo` and `in-progress`). |
| `wrk list --all` | Include done and canceled tickets. |
| `wrk list --ready` | List only `todo` tickets whose dependencies are all `done`. |
| `wrk show <id>` | Show the full ticket, its children, and dependency blockers. |
| `wrk update <id> --title "New title"` | Change the title. |
| `wrk update <id> --status in-progress` | Change status; accept all four defined statuses. |
| `wrk validate` | Check config, tickets, IDs, and relationship integrity without writing files. |

Allow title and status flags to be combined into one validated update. Reject contradictory list flags such as `--all --ready` with a useful error.

## Acceptance criteria

- [x] Document and verify installation or local execution from a fresh checkout.
- [x] Implement the command contract above; running `wrk` alone displays help.
- [x] Commands run without interactive prompts and report useful errors with nonzero exit codes on failure.
- [x] Provide readable default output and `--json` for each command's result, including affected IDs and paths for mutations.
- [x] Discover the nearest `.wrk/` from any project subdirectory and read its config; invalid inner configuration must not fall through to an outer project.
- [x] Honor prefix and creation defaults, and validate the existing configuration and custom-field definitions.
- [x] Read this project's existing tickets and relationships without requiring a migration.
- [x] Generate stable, unique local IDs and never overwrite an existing ticket on creation.
- [x] Preserve the Markdown body exactly and preserve unrelated metadata and custom-field values during title or status updates.
- [x] Validate changes before writing; failed operations leave existing files unchanged and concurrent edits are not silently overwritten.
- [x] Report invalid config or metadata, ID/filename mismatches, duplicate IDs, missing references, self-references, duplicate dependencies, and cycles in each relationship graph.
- [x] Report unfinished dependency blockers without prohibiting explicit status changes or automatically changing other tickets.
- [x] Cover the core workflow, config discovery, body preservation, existing metadata preservation, JSON output, and validation failures with meaningful automated tests.
- [x] Add working command examples to the README and update agent docs to explain which metadata changes the CLI supports.
- [x] Use the CLI to show this ticket, mark it `in-progress` once updates work, create follow-up tickets for deferred metadata commands, and mark this ticket `done` when its criteria are met.
