## Outcome

Record when an item was created as built-in `created_at` metadata, consistently across `wrk new` and `wrk serve`, and make the timestamp available to people and API consumers.

## Decisions and scope

- Store `created_at` as a top-level frontmatter field, not a custom value under `fields`.
- Automatically assign the timestamp in the shared creation path using the current UTC time, serialized as RFC 3339 with a `Z` suffix (for example, `2026-10-15T18:42:03Z`).
- Treat the value as immutable through supported CLI and HTTP mutations. Ordinary edits must preserve it; no creation-time override or timestamp-editing controls are needed.
- Keep the field optional for existing items. Missing dates mean unknown; do not infer dates from Git or filesystem metadata, backfill them on reads/edits, or require a migration.
- Do not add `updated_at`. Date sorting/filtering and historical backfill are outside this ticket.

## Acceptance criteria

- [x] Extend the ticket model, frontmatter parser, validation, and serialization to support `created_at`. Document accepted timestamp syntax and reject malformed supplied values with actionable diagnostics, while accepting legacy items without the field.
- [x] `wrk new` automatically persists `created_at`, including when creating children or supplying metadata/body values. Creation assigns the value once and retains it across internal publication retries.
- [x] CLI JSON summaries and applicable creation/list/show output expose the stored date consistently. Document how missing dates are represented; never substitute a zero date or the current time.
- [x] `wrk serve` POST `/api/items` assigns the timestamp on the server through the same shared creation path. Cover both the browser creation modal and inline child creation.
- [x] HTTP creation responses and read APIs (`/api/items`, `/api/items/<id>`, `/api/workspace`, and nested item summaries) expose `created_at` consistently with CLI JSON.
- [x] The browser detail panel displays the creation date as read-only metadata with an unambiguous timezone. Items with no date render gracefully without an invented date or an error. Refresh/polling reflects the value for newly created items.
- [x] CLI updates and browser/API edits, including body, metadata, status, and relationship changes, preserve existing timestamps and leave absent dates absent. HTTP clients cannot set or change the server-managed field.
- [x] Add meaningful unit/integration coverage for both creation entry points, valid/invalid/missing dates, JSON/API output, timestamp preservation, and legacy items. Verify browser display and both browser creation flows.
- [x] Update `docs/ticket-format.md`, `docs/cli.md`, and `docs/browser.md` with the format, output, display, and compatibility behavior, including implications for older clients. Update the docs index if new guidance needs an entry.
- [x] Run the relevant development checks and `go run ./cmd/wrk validate`; record results and any remaining limitations here before closing the ticket.

## Context and handoff

The user approved automatic creation timestamps and explicitly excluded `updated_at`. Implementation and verification are complete.

Before this change, the format had no built-in timestamp metadata. Implementation spans `internal/ticket`, shared store creation/summary code, CLI output, and browser detail rendering; HTTP handlers inherit the shared creation and summary behavior. Existing preservation, writer-lock, and stale-edit contracts remain in force.

## Implementation decisions and progress

- Shared store creation captures UTC time once before ID/publication retries. New files store whole-second RFC 3339 timestamps with `Z`.
- Readers accept quoted strings or YAML timestamps with uppercase `T`, `Z` or numeric offset, and optional 1–9 fractional digits. Validation checks calendar/time/offset ranges. Stored spelling and YAML type are preserved.
- Every CLI/HTTP summary has `created_at` as a stored string or `null`. Human lists add `CREATED_AT` (`unknown` for legacy items); human creation prints the timestamp; show retains exact source.
- Browser details display a read-only UTC date (millisecond display precision, full stored value in the time element/tooltip), or “Created date unknown.” Neither CLI flags nor HTTP request fields allow overriding the timestamp.
- A timestamp alias regression test exposed the YAML encoder quoting implicit timestamps inside flow collections without their type tag. The emission graph now retains explicit timestamp tags in that context so ordinary edits preserve valid aliased timestamps.
- Focused ticket/store/CLI/API checks cover strict syntax, absence, creation, retries, nested summaries, rejected overrides, and preservation. Browser and complete development verification passed.
