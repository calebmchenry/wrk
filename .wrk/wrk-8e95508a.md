## Outcome

`wrk run --stream` waits for previously unprocessed tickets to match the selected query, while ordinary mode exits when its current work is drained.

Depends on [wrk-59020e2f](wrk-59020e2f.md). Preserve the parent contract in [wrk-0a233d21](wrk-0a233d21.md).

## Behavior

- Add `--stream` on run, not list, and an idle `--poll-interval` with a default of 5s. Validate a positive duration before launching work; define unsupported flag combinations, including one-off `--ticket`, in help.
- Poll only when no unprocessed matching ticket exists. Wait with an interruptible timer rather than a busy loop. After a successful action, re-query immediately; never select or queue the next action while the current child is running.
- Keep the core invocation's successful-ID set across every poll. A successful review may leave a ticket ready, but it runs only once during this invocation. Leaving/re-entering the query or reopening the ticket does not clear the set. A fresh command invocation may process the ticket again.
- New tickets and previously unseen tickets becoming eligible through dependency/status/label changes can be selected on a later poll. Project selection, filter semantics, and existing ordering stay fixed.
- Streaming changes only idle behavior. Child failures, failed expected-status checks, invalid project data, selection errors, and log/output failures still stop. Do not reinterpret these as an empty query or automatically retry.
- Success-count limits still end the run. Interruption while waiting exits promptly; interruption while running uses the same process-group cleanup as the core.
- Distinguish raw matches, already processed matches, and unprocessed candidates. A nonempty raw query with every match processed is idle, not a reason to spin or run tickets again.
- Expose entering/leaving idle, current selection counts, elapsed idle time, and relevant scope-state changes to the output layer. Do not claim an empty ready query means the project's work is complete.

## Acceptance criteria

- [x] Implement interruptible idle polling and validate flags/durations without changing ordinary run behavior.
- [x] Preserve sequential execution, once-per-invocation processing, strict failure stops, fixed project/scope, and success limits across polls.
- [x] Add deterministic tests for initial emptiness followed by new work, dependency unlocking, previously unseen tickets entering the filter, and completed IDs remaining/re-entering the query.
- [x] Test an all-processed nonempty query, multiple idle polls without rerunning actions, immediate reselection after success, interruption during idle, and the success limit.
- [x] Verify that a failed child/completion check or invalid project during a later poll stops rather than silently waiting/retrying.
- [x] Provide idle lifecycle data for readable human output and JSON without repeated empty-query spam.

## Scope

No daemon/service installation, background scheduling, filesystem watcher, concurrent worker, persistent processed-ID registry, or workflow resume mechanism. The invocation-local set may grow with successful work; it must not be silently reset to keep a long run active.

## Implementation

- Add `run --stream` with an idle-only `--poll-interval` (positive Go duration,
  default 5s). An explicit interval requires streaming; one-off `--ticket` and
  `list --stream` remain unsupported.
- Reuse the sequential engine, pinned project/query, and successful-ID set.
  Wait only after a valid query has no unprocessed candidates; action success
  still triggers immediate reselection, and all failures remain terminal.
- Provide `idle_started`, `idle_changed`, and `idle_finished` engine events with
  raw/processed/unprocessed counts, elapsed idle time, and mutually exclusive
  scope status counts from the same snapshot. Suppress unchanged idle polls.
  Baseline human rendering consumes those events; detailed logs, heartbeat, and
  NDJSON rendering remain in wrk-7b831fa1.
- Deterministic engine tests mutate disposable projects at the idle wait boundary;
  virtual-time tests verify the production timer's interval and cancellation.
  Coverage includes new work, dependency/status/label/parent changes, reopened and
  returning IDs, repeated idle periods, immediate reselection, success limits,
  scope counts, child/check/project/selection failures, and event/child-output errors.
- Compiled-CLI tests cover invocation-relative config selection, new work during
  idle, usage validation before launch, ordinary JSON results, invalid later
  snapshots, idle SIGINT/SIGTERM, and process-group cleanup in both run modes.
- Updated help and indexed CLI documentation describe polling and the event handoff.
