## Outcome

Run wrk serve to browse and edit the selected project's .wrk items in a local browser, with changes from agents and the CLI appearing automatically. The files remain the source of truth.

## Confirmed intent (2026-10-08)

The user confirmed local-only use, emphasized watching agents make changes live, and authorized creating and organizing implementation tickets. The original requested workflow includes creating items, changing status, linking, parenting, and tagging. The user subsequently authorized picking and implementing work; implementation began with shared body updates and stale-edit preconditions in wrk-27b71a32.

Discovery is recorded in [wrk-4036f7d4](wrk-4036f7d4.md).

## Batch decisions

- One local project per server process; bind only to loopback. No accounts, shared-team hosting, or remote service.
- Default to existing nearest-.wrk upward discovery. Support --project and --config for a different existing project, with explicit selection overriding cwd.
- Bundle the UI in the wrk executable. No database, CDN, external service, or frontend development server is needed to use a built release.
- Use a searchable list and item detail pane first. Make live updates a core deliverable, before adding browser writes.
- Support title and Markdown body editing, all existing statuses, labels, parent/children, and dependencies. Preserve priority and custom fields; custom-field form building is outside this batch.
- Add a small general related-to relationship, distinct from parenting and prerequisite dependencies.
- Reuse the existing Go project/store validation and publication paths. Add protection against browser edits based on stale item versions.
- Status changes stay explicit. Progress counts and links do not introduce automatic transitions.

## Acceptance criteria

- [x] Start from a project, a nested directory, or an unrelated directory with an explicit selector; the browser clearly identifies the selected project.
- [x] Serve on a predictable default or requested port, including automatic allocation with --port 0, with bundled assets and clean shutdown.
- [x] Search and inspect items, Markdown descriptions, labels, statuses, hierarchy, blockers, and related links.
- [x] Display external item/config changes within two seconds under normal local operation, with reconnect/recovery and visible invalid-project diagnostics.
- [x] Create and edit the requested item fields through shared validated storage; preserve unsaved drafts and reject stale saves.
- [x] Verify the complete browser-plus-agent workflow on macOS and Linux and document invocation, boundaries, and recovery.

## Implementation progress (2026-10-08)

Shared safe body updates and revision preconditions (wrk-27b71a32) and explicit project/config selection (wrk-47b4e027) are implemented and verified on macOS and Linux. The CLI replaces bodies from a file/stdin and exposes source revisions; the store can reject stale single-item saves. Browser views (wrk-fa8c7f1f) are now implemented: searchable list/detail panes, intersecting filters and parent focus, safe Markdown, relationship navigation, original custom YAML, and URL/history/list-position preservation. Seven Chromium scenarios pass, with desktop and narrow screenshots visually inspected; this verifies the browsing UI that the earlier shell test could not display. Remaining work is live refresh, browser editing, related links, and full workspace acceptance. Live refresh (wrk-ce7350ff) is next; the final workflow ticket still owns full browser-plus-agent acceptance.
